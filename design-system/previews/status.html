Status & verdicts

These components take the raw database enum as a data-* attribute and pick their own tone, so a status cannot be mis-coloured at a call site.

Requirement status

The enum name eval_failed is misleading and must never reach a screen. Per the lifecycle spec, a negative verdict from the Evaluator writes eval_failed; it does not mean the evaluation errored. It renders as "Not satisfied". A genuine system failure is a separate component, below, in a different colour.

new is neutral rather than amber on purpose: never having been evaluated is an absence of information, not a warning. And archived is not a status at all — it comes from requirements.archived_at, which is orthogonal to version status; it appears here only because a row shows one badge at a time.

System error — not a verdict

A GitHub rate limit mid-run, an evaluator crash, or a request that hit the serverless execution ceiling. Coral, never periwinkle. None of these say anything about whether the code satisfies the requirement, and showing them in the verdict colour would tell the developer something false.

Version pills

The current version is resolved through requirements.current_version_id at read time — never stored on the requirement row, because two copies of the same fact desync.
