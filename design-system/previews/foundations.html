Foundations

Colour, type, space and motion. Every value is a CSS custom property in styles/tokens.css — nothing downstream contains a raw hex.

Surfaces

A five-step ramp. Inset is darker than the canvas, not lighter: evidence (commit lists, digests, log refs) reads as a well cut into the page, while chrome sits above it on cards. That inversion is the core of the look.

--ds-color-canvas
Page background
--ds-color-surface
Cards, panels
--ds-color-surface-raised
Menus, toasts, secondary buttons
--ds-color-surface-hover
Row and control hover
--ds-color-surface-inset
Wells, inputs, identifiers
--ds-color-border
Hairline · carries all structure

Accent

Signal amber, used only for interactive affordances: primary actions, links, focus, active nav. Deliberately outside the verdict family so it can never be misread as a result. Two values, because one cannot do both jobs accessibly: accent for text on dark (≈10.5:1), accent-solid for fills. Note that fills carry near-black text, not white (--ds-color-on-accent, ≈9:1), because amber is a light fill and white on it fails at any size.

--ds-color-accent
Text, icons, links
--ds-color-accent-solid
Filled backgrounds
--ds-color-accent-subtle
Selected rows, active nav

Status

Four tones, each bound to one meaning. The subtle one is the middle pair: a negative verdict and a system failure are different events and never share a hue. A rate limit or a blown execution ceiling says nothing about whether the code satisfies a requirement, so it gets coral, while a genuine "not satisfied" gets periwinkle. Neutral, not amber, marks new: "not yet assessed" is an absence of information, not a caution.

--ds-color-success
status verified · verdict satisfied
--ds-color-verdict-failed
status eval_failed · verdict not_satisfied
--ds-color-danger
True errors & destructive actions · never a verdict
--ds-color-neutral
status new · never evaluated

Role identity

Two hues kept clear of both the amber accent and every verdict colour. Who someone is must never be confused with what an evaluation concluded.

--ds-color-role-stakeholder
Defines requirements, reads reports
--ds-color-role-developer
Attaches repos, submits claims

Typography

A numeric scale, so "is 400 larger than 300" is never a question. 300 is the default UI size; 400 is the reading size and is used only where there are real sentences: evaluator rationales and requirement descriptions. Monospace is not decorative here: it marks every value a person might paste into a terminal.

--ds-text-700 · 26/34 · semibold
Requirement verification
--ds-text-600 · 20/28 · semibold · page titles
Rate limiting on /api/claims
--ds-text-500 · 16/24 · semibold · section headings
Claimed commits
--ds-text-400 · 14/22 · prose, rationales

The token bucket limiter is applied to the claim submission route and covers both the per-developer and per-project ceilings described in the requirement. The refill interval is configured at the value the requirement specifies.

Space & radius

A 4px base, eight rungs. Radii stay sharp: nothing exceeds 8px except full pills.

space scale · 4 8 12 16 24 32 48 64
density contexts · row-dense 36 (commit lists, tables) · row-comfy 48 (checklist rows)
radius · sm 3 · md 4 · lg 6 · xl 8 · full
control heights · sm 24 · md 30 · lg 36 — shared by every interactive control so buttons and inputs always align
